# Hutch v0.2.1

Fixes for running several machines, and a lead that only coordinates. See [several machines](https://github.com/mouizahmed/hutch/blob/main/docs/machines.md) and the [v0.2.0 notes](https://github.com/mouizahmed/hutch/blob/main/docs/releases/v0.2.0.md).

## New

- **A lead that only coordinates.** `hutch setup <ssh-host> --no-boxes` sets up a machine with no box requirements (no KVM, kernel 6.1, XFS, or box runtimes) that places boxes on the machines you add. It's refused on a machine that already has boxes or belongs to a setup.
- **Doctor across machines.** It names a machine that was added but never connected, and from a machine that's offline it tries the lead's link port over SSH, so a blocked firewall or security group shows as such.

## Fixes

- An old lead fenced by `hutch machine lead --from-backup` can be added back with `hutch machine add`, as documented; v0.2.0 refused it as holding another setup's boxes.
- `--down` is checked more strictly: a worker restarted while cut off from the lead still writes its heartbeat, the lead keeps writing its own while it leads, and a heartbeat's age is measured by the bucket's clock rather than this computer's.
- The one-way bucket format question is asked once before the lead is upgraded, and also for upgrades to v0.2 pre-releases.
- `hutch machine upgrade` skips workers already on the new version, and when a worker isn't upgraded it names the actual cause.
- `hutch shell` returns to your terminal when the shell exits, instead of showing another of the box's terminals.
- Upgrading from a build made from source no longer needs `--force` when the new version is later.
- The release workflow creates its draft release only after the client checks pass on Linux, macOS and Windows.

## Upgrading

`hutch machine upgrade` upgrades the lead, then every worker. Running boxes keep running.
