# Hutch v0.2.0

More capacity is another machine. The first machine's `hutchd` leads; other machines join as its workers and dial out to it, so a machine at home or behind a router needs no open port. One `machine` setting on your computer still reaches every box. See [several machines](https://github.com/mouizahmed/hutch/blob/main/docs/machines.md).

## What's new

- **Adding machines.** `hutch machine add <ssh-host>` installs `hutchd` on another machine and enrolls it with a one-time token over mutual TLS. Firecracker and gVisor machines can work side by side. `hutch machine` lists them.
- **Placement across machines.** A new box goes to a machine that fits it and preferably already has its template version; `placement.order` fills the fullest (`fill`, the default) or spreads to the emptiest (`spread`). `hutch new --on <machine>` places or queues a box on one machine. `hutch ls` and the TUI show each box's machine.
- **Per-machine settings.** `hutch config set --on <machine>` overrides a machine-layer key for one machine, over `--machine` for every machine. New keys: `machine.max_boxes` caps a machine's awake boxes, and `machine.run_boxes = false` makes a machine coordinate only.
- **Moves and removal.** `hutch move <box> --to <machine>` moves warm within a snapshot class and cold across classes. `hutch machine rm <machine>` moves every box off a machine, then removes it. A box waiting to wake on a full machine moves to another of its class after `placement.move_queued_after`.
- **Lost machines.** `hutch machine rm --lost <machine>` fences a machine that's gone and brings its boxes back elsewhere from their newest snapshots. Hutch never does this on its own; it notifies you when a machine stays unreachable for `machines.lost_notify_after`.
- **Changing the lead.** `hutch machine lead <machine>` hands the lead to another machine with nothing lost. `hutch machine lead <ssh-host> --from-backup` promotes a worker when the lead is dead. Leads are numbered by term in a signed record in the bucket; an old lead that finds a higher term stops leading, keeps its state aside, and rejoins as a worker with `hutch machine add`.
- **Logins on workers.** The keys proxy's CA key, the identity signing key and the master key stay on the lead. A worker holds only the logins of the boxes it runs, in memory, and gets certificates and identity tokens signed by the lead. Token refreshes go through the lead, so two machines never race a rotating refresh token.
- **Working through an outage.** While the lead is unreachable, a worker's own CLI can list, attach to, exec in, forward ports of, sleep and wake that worker's boxes.
- **Operations.** `hutch machine upgrade` upgrades the lead, then every worker, checkpointing running boxes first. `hutch doctor` reports each machine's checks, its link, its view of the bucket, and the lead record.
- **Configuration.** `hutch config unset <key>` removes a setting from one layer. `hutch config set` accepts lists written as TOML arrays as well as comma-separated.

## Upgrading from v0.1

Install the new CLI, then run `hutch machine upgrade` and `hutch doctor`. Running boxes are checkpointed and keep running.

- **There's no way back to v0.1.** v0.2 names box snapshots in the bucket by a stable ID and an ownership number, and raises the bucket's format. v0.1 can't read the new names. Existing boxes keep their old names until they move. `hutch machine upgrade` says so and asks before the first upgrade from v0.1 (`--yes` skips the question).
- **Backups are named by lead term.** A restore takes the newest backup of the highest term; v0.1's backups count as term 0.
- **A single machine works as before.** The worker link and its port open only once a second machine is added.

## Requirements for several machines

- A backup bucket on the lead (`hutch machine bucket`): workers write their boxes' snapshots to it. Its credentials are on every machine.
- The lead's link port, 7443 (`machine.link_port`), reachable from each worker. Workers need no inbound port.
- SSH from your computer to every machine, for adding, upgrading and fencing them.
- Every machine on the same `hutchd` version for a planned handover. `hutch machine upgrade` keeps them together.

## Current limitations

- A lead that dies isn't replaced automatically: you run `hutch machine lead --from-backup`. Hutch can't tell a dead lead from one that's only cut off from the others, and replacing one that's still working would make two leads. Changes made since the last backup (`backup.interval`) are lost, apart from boxes, which are recovered from the workers' reports.
- A login refreshed after the last backup is lost if the lead dies before the next one; the provider then refuses the old token, and Hutch asks you to `hutch login` again.
- `--down` is your word that a machine you can't fence is off. Every machine writes a heartbeat to the bucket each `machines.lead_check`, and `--down` is refused while that's recent, so a machine still working with the bucket is caught. One that's running but cut off from the bucket too isn't; it can't write to the bucket, and it gives up its boxes or its lead once it can reach it again and reads the newer term.
- A lost machine's boxes come back from their newest snapshot (`checkpoint.interval`); work since then is lost.
- The bucket's credentials on every machine can delete objects. Turn on the provider's object versioning or retention.
- Warm moves need the same snapshot class on both machines; across classes a box boots cold, keeping its files.
- Machines are x86_64 only, as in v0.1. The [v0.1.0 limitations](v0.1.0.md#current-limitations) otherwise still apply, except one machine per setup.

## Validation

Tested on a disposable AWS rig of three machines: a lead and a worker with Firecracker, and a gVisor worker with no inbound port. The tests covered:

- placement, moves warm and cold, and draining a machine;
- a worker's instance stopped mid-task and its boxes restored elsewhere;
- a network partition, and stale copies returning as `<box>-returned`;
- three planned handovers with work running in boxes on two machines;
- a dead lead promoted from the bucket, a paused lead fenced, and a false `--down`;
- Claude Code and Codex on two machines, with a refresh on one used by the other.

CI runs the daemon upgrade from v0.1.0 on both backends.
