# Hutch v0.1.0

Hutch gives coding agents their own working environments on a Linux machine you rent or own. Prepare a project's environment once, create boxes from its snapshots, and reconnect to persistent terminals from your computer.

This initial release focuses on one machine, accessed through SSH.

## What's included

- **Project templates and snapshot-based boxes.** Build an environment from your project recipe, verify it, publish template versions and create independent working copies. Idle boxes sleep; compatible warm restores retain running processes.
- **CLI and TUI.** Switch between projects, boxes and live agent or shell terminals. Terminals in a box share its files and services. Activity and unread indicators help track work while you switch views or disconnect.
- **Native agent workflows.** Built-in adapters for Claude Code, Codex and GitHub CLI, plus TOML adapters for other command-line agents. Git handoffs move commits and supported agent sessions between your computer and a box.
- **Configuration sync and MCP support.** Sync adapter-declared configuration and MCP settings. Agents can launch stdio MCP servers inside their boxes or connect to remote HTTP servers. A standalone HTTP MCP can also run in its own ordinary box.
- **Scoped credential forwarding.** A host-side HTTPS proxy substitutes supported agent, GitHub and MCP header credentials according to box grants and destination hosts, and coordinates managed OAuth refreshes. Optional signed box identity lets configured HTTPS services identify the calling box and project.
- **Private service forwarding.** Reach a box service on your computer with `hutch forward`. A named-port listener remains available while the box sleeps; an incoming connection wakes it, and open forwarded connections keep it awake.
- **Backup, recovery and maintenance.** Optional encrypted S3-compatible backups, machine recovery, checkpointed daemon upgrades and `hutch doctor` diagnostics. Template diagnostics build twice, run verification, compare fingerprints and probe declared MCP servers.

## Install

Install on Linux or macOS with:

```sh
curl -fsSL https://github.com/mouizahmed/hutch/releases/latest/download/install.sh | sh
```

The installer checks the archive's SHA-256 and installs into `~/.local/bin`. Windows users can use the matching `hutch.exe` archive or WSL. CLI archives cover amd64 and arm64 on Linux, macOS and Windows.

Start with the [VPS quick start](https://github.com/mouizahmed/hutch/blob/main/docs/quickstart.md). It covers machine setup, native sign-in, configuration sync and the first project template.

## Machine requirements

Use an x86_64 Linux machine with systemd, kernel 6.1 or newer, and passwordless SSH/sudo access. Setup prepares XFS storage with reflink support. Eight GB of RAM is a practical starting point.

Machines with KVM use Firecracker microVMs. Machines without KVM use gVisor sandboxes, whose workload compatibility and isolation differ. ARM computers can run the CLI; ARM machines are not supported in v0.1.

## Current limitations

- One machine per setup. Public token-protected service URLs and automatic connections between dedicated MCP boxes and other agent boxes are not included. Laptop access uses private SSH forwarding.
- Public internet egress is open. Domain-restricted `allowlist` mode is not implemented; requesting it refuses box startup.
- Credential substitution covers supported HTTPS header tokens. Native MCP OAuth caches, unsupported credential types and uploaded project secrets can remain real inside boxes and snapshots. Laptop keychains and MCP OAuth sessions do not automatically transfer. See the [security model](https://github.com/mouizahmed/hutch/blob/main/docs/security.md).
- MCP commands and their dependencies must exist inside the box. Hutch's TUI shows their terminal output; it has no dedicated MCP health or authentication panel.
- Terminal activity indicators do not establish agent intent or MCP readiness. Agent conversations and resume behavior remain managed by the native agent.
- Cold boots preserve files but restart the environment. Agents resume through their native pickers. Incompatible imported snapshots, including gVisor snapshots with unknown or unsupported CPU requirements, restore cold.
- Forks cannot narrow the credential grants of their source snapshot. Native Windows handoffs transfer code; agent conversations stay on their original side.
- Authentication uses a fresh temporary login box and may download the requested agent CLIs again. Without a backup bucket, losing the machine loses its boxes.

## Existing development setups

Boxes created before the keys proxy may still hold real credentials. Preserve their code and agent sessions, stop their old agents, and migrate work into boxes from rebuilt templates before using them again. Reauthenticate managed accounts with the old refreshers stopped. A daemon upgrade alone does not scrub credentials from old disks or snapshots.

## Validation

Validation covers Linux/macOS/Windows client checks, both runtime backends, lifecycle and recovery, snapshot exchange, native MCP compatibility and an automated fresh-account install rehearsal. Claude Code 2.1.314 and Codex CLI 0.166.0 passed real authentication and refresh checks, including concurrent-box sharing and persistence across daemon restart. These authentication checks did not submit model inference requests.
